## Root Cause

This group is not one bug. `ValidationException` is the client's own protovalidate check
(`request.validate().orThrow()` before each RPC, e.g. `ChatApi.kt:255`), converted at
`Throwable.kt:11`. Because it extends `CodeServerError`, `ErrorUtils.kt:65` makes it not
notifiable, and Bugsnag groups every field on the `CodeServerError.<init>` frame. The eight
fields have three different causes:

#86's last-30 sample overweighted the two Internal-only fields. Over the whole group,
`message_ids` is 1,022 of 1,057 events and stops before the fix. The only open client bug on a
production build is the short mint (`addresses`/`address`, 8 events, 2026.10.3 latest).

The username failure is not user input, contrary to #86. The user never typed into this
request; the server accepted a handle the app's pinned contract rejects.

## Evidence

- **Exception**: `ValidationException`: `Request validation failed: <field>: <rule message>[, …]`
  (`ValidationException.kt:10` joins every violation into the message)
- **Key stack frame**: `ThrowableKt.toValidationOrElse` (`Throwable.kt:9`) under each service's
  `foldWithSuppression`
- **Log excerpt**: `[TokenController] Failed to batch-fetch token metadata: Request validation
  failed: addresses[0].value: must be at least 32 bytes`, preceded by `Batch-fetching token
  metadata for 1 mint(s) from network` (event `6adfe08c019b37b0ad1d0000`). The short request is
  never logged, since validation throws before the RPC.
- **Breadcrumb trail**: mint failures follow `MainActivity#onResume` / token hydration on app
  start, not a deeplink. `user_id` failures follow `Authenticating => Ready` and
  `onUserLoggedIn`.
- **Device**: spread across users; not device-specific.

## Fix Direction

1. **Decision 3: make validation failures notifiable selectively, not for the whole class.**
   The open client bugs (`addresses`, `address`, `user_id`) confirm the "if it confirms a client
   bug" branch. The three user-input fields need UI guards, not `WARNING`. Pin drift needs the
   contract bump, which is already on `code/cash`. Today the exception can't tell these apart:
   `Throwable.kt:12` keeps only `field` and `message`. A follow-up brief should decide how call
   sites mark user-input requests (e.g. a flag on `ValidationException`, or classifying by
   request type) so programmatic fields report `WARNING`.
2. **Short mint:** add a 32-byte check where a string becomes a `Mint` (`Mint.kt:10`; the
   Parcelable creator at `Mint.kt:14` falls back to `""`, and `AppRouter.kt:431` passes a raw path
   segment) and make `TokenCoordinator.getTokenMetadata` fail fast with the source logged. That
   names the real caller the stack doesn't. Candidates: the persisted selected-token mint
   (`TokenCoordinator.kt:515`, `:719`), Room `mintBase58` (`MessageEntity.kt:35`), and the token
   route arg. Hypothesis, not confirmed.
3. **`user_id`:** have `clear()` set `accountId = null`, or treat an empty ID as missing at
   `AccountController.kt:32` / `ProfileController.kt:27`. Likely, based on two events.
4. **UI guards:** reuse the 64-code-point `ChatTitle` rule in Create Group; apply the display
   name bound for every source; check the currency name against the contract pattern before
   `checkTokenAvailability`.
5. **Grouping hash (Decision 4):** class plus message gives 100 distinct groups here. Stripping
   `[N]` and de-duplicating repeated violations gives 9. Hash on the sorted set of
   `field path with [N] removed + FieldViolation.rule`, not the message: the message carries the
   contract bound, so the `{2,15}` → `{2,30}` bump would split the username group again. This
   needs `Throwable.kt:12` to carry `rule` through to `Violation`. Without it, hash on field paths
   alone (8 groups); the cost is that `display_name` too long and too short share a group. The
   messages carry no request values, so nothing else needs stripping.

Risk: a `WARNING` for programmatic fields will also report the next pin drift. That is probably
wanted, but the reporting would surface server rollouts ahead of the client bump.
